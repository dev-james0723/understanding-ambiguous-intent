# Exploratory UAI forward checks

This run uses 16 UAI-only public development boundary cases and four live trajectories comprising 13 user turns. The boundary cases are shuffled with Python `random.Random(20261125).shuffle`, then assigned opaque IDs. Each boundary case begins a fresh actor with the serialized case conversation. No case title, category, label, rubric, or expected response is supplied. The exact UAI runtime skill, with SHA-256 `5633377efaaa9b85fd9ed0fddfb62e45fe0b3f8d9db3c1cd7dcf8088c849b3fd`, follows the same base instruction as the matched comparison.

Each trajectory uses one fresh actor. The initial request contains the base and skill instructions and just the first user turn. Subsequent user messages are sent to the same actor as plain text after the previous answer is captured. The coordinator materializes each next request only after recording the preceding answer. The actor is instructed to put the exact answer in its response file and supply the same answer as its final message, so it continues from its own previous answers. The trajectory records preserve the exact user messages, exact answer text, and replay prefixes. The expected future turns and rubrics are not supplied to the actor. The actor retains the initial wrapper and its own host-level file interactions as part of its session.

The only response-generation surface is ChatGPT collaboration. Actors request `gpt-6.2-sol`, high reasoning effort, and no inherited conversation. The host does not expose the resolved configuration, token usage, or provider latency. The coordinator permits up to two active children at a time, subject to the collaboration slot limit. Actor-specific directories are outside the repository. The wrapper limits each actor to its own request and output files and disallows task tools, browsing, agents, or external effects. Tool isolation is prompt-enforced, and the operating system does not restrict directory access. The harness applies the skill as instruction text without native host triggering. These are synthetic development and regression fixtures with one trial per case or trajectory. No behavioral grading is performed by the coordinator.

The append-only manifest records queued turns, launches, and terminal outcomes. Response ledgers store attempts within each group. Input hashes cover the exact request file contents, or the exact subsequent user message delivered in a live trajectory. SHA-256 response hashes cover exact bytes. An `ok` status means the recorded answer is present and readable. A boundary actor may be retried once after checking whether an answer file exists. Trajectory interruptions are recorded separately because a fresh actor cannot preserve the original live history.

## Completed run

The run captured 16 boundary answers and 13 answers from four live trajectories, with no retries or failed attempts. Each of the 20 actor threads was unique to its assigned boundary case or trajectory. The coordinator compared the trajectory answers against their actor final messages, validated replay prefixes and fixture turns, and verified exact input and output hashes. The 87 lifecycle events include one queued, started, and terminal record for each of the 29 answers. The original matched-comparison response and manifest ledgers retained their prior hashes.

## Publication and review

The raw trajectory ledger is retained as trajectory-attempts.jsonl. The published trajectory-responses.jsonl derives unique per-turn sample and case IDs by appending #turn-N; it retains the original identifiers in trajectory_sample_id and trajectory_id. Response bytes, hashes and replay prefixes are unchanged. A separate review agent receives only exact prior conversation, answer and per-turn rubric, with no condition labels or runtime instructions. The integration agent checks boundary coverage, hash links and borderline outcomes. These are agent-reviewed development checks, not human evaluation or a comparative benchmark.
